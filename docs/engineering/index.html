How Senderban is built

A small tool that holds mail passwords and writes rules into your mailbox has to be careful. These are the decisions behind it, each one written down before the code, with the reasoning and the cost.

  • TypeScriptstrict, Node 24, Electron
  • 5 adaptersGmail, Graph, ManageSieve, MXroute, IMAP
  • 18 ADRsone per decision
  • 0 serversruns on your device only

Architecture

Two packages. The core knows nothing about Electron or Windows; the desktop app knows nothing about any one provider. A provider is an adapter behind one interface.

Your mail provider

The rule lives here, so it holds on every device

Write, then read back

Every block is planned, applied and then read back from the server. A rule that did not land is reported, never assumed.

Only its own rules

Senderban writes rules marked as its own and leaves yours alone. A Sieve script it did not write and cannot parse is never edited.

Headers only

A new mail costs one fetch of From and Subject, plus the spam score where the server adds one. There is no sync and no message body.

Finds the way in

From an address alone it reads MX and SRV records (RFC 6186) through the system resolver, drops private and loopback addresses, and fills in the server.

Security model

Every byte that arrives from a mail server, a sender, a file or the window is treated as hostile until it is parsed.

Window
Renderer runs with sandbox, contextIsolation and no Node integration. CSP is default-src 'none' with local scripts and styles only. New windows and navigation are refused.
IPC
Each handler first checks the message came from our own window and frame, then parses its input with a strict Zod schema. Unknown fields are rejected.
Input limits
Bounds come from the meaning of a value, not a character cap: an address follows RFC 5321 (local part 64, domain 253, whole 254), a time is in seconds with a minimum and a maximum, and the same number holds in the window, the schema and the store.
Secrets
Passwords and tokens are encrypted with the operating system's key through Electron safeStorage. If encryption is not available, Senderban does not store the secret.
Sign-in
Gmail and Outlook use OAuth with PKCE, state and a loopback redirect (RFC 8252). Scopes are the least that work: Gmail gmail.metadata and gmail.settings.basic; Microsoft Mail.ReadBasic and MailboxSettings.ReadWrite.
Fail closed
When a server answers with something Senderban cannot read, it stops and says so. It does not guess, retry blindly or delete.

Scale budget

Written before the code: what one account costs, and what 10 and 50 cost. Cost grows with accounts, never with mail volume. Shared resources go through one gate each, and every gated job has a deadline, so one stuck account cannot hold the others.

Quantity 1 account 10 50
Persistent IMAP connections 1 10 50
Logins in flight after resume 1 5 5 (gate, tested)
ManageSieve commands per block 10 64 304 (measured)
Rules script, 1,000 entries 53 KB (measured)

Every number is tagged measured, derived or unmeasured. Full table and known costs: ADR 0006.

How it is checked

Every push runs the same pipeline, and the release is built only from a version tag.

  1. Type check
  2. Build
  3. Lint
  4. Format
  5. Tests
  6. Identifier check
  7. Secret scan of the whole history

Measured, not claimed

A provider is marked tested only after it ran against a real account. Everything else says what it was tested on.

Release provenance

The installer is built by the release workflow and gets a signed build attestation. The job that signs never runs dependency code.

Verify a download

Compare the hash with SHA256SUMS on the release, then prove the file came from the tag's release workflow (needs the GitHub CLI): 

Get-FileHash .\Senderban-Setup-X.Y.Z.exe -Algorithm SHA256

gh attestation verify .\Senderban-Setup-X.Y.Z.exe --repo senderban/senderban `
  --signer-workflow senderban/senderban/.github/workflows/release.yml `
  --source-ref refs/tags/vX.Y.Z --deny-self-hosted-runners
