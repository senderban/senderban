Finding a mail provider from an address, when DNS can lie

Senderban's Find my provider button turns an address into a server name. The input comes from unsigned DNS, and the output decides where a mailbox password goes. This is how it is built so that a forged answer reaches nothing, what leaves the device, and what it gives up for that.

The problem

A person knows their address, not which company runs their domain or which server name to type. A custom domain says nothing about who hosts it; only its DNS records do, and DNS is unsigned. On a hostile network, anyone can answer it. And the person who presses this button is exactly the person who cannot tell a right server name from a forged one, so a design that asks them to compare names protects nobody (ADR 0018).

A red-team pass over the code on 1 November 2026 made it concrete. Forge one SRV record, _imaps._tcp, so it names a host the attacker holds a valid certificate for. The form fills in that host, the person types their password, and it goes over verified TLS to the attacker. TLS works as designed: the certificate proves the name, and the name came from the attacker. RFC 6125 §6.2.1 says a reference identifier should not come from a DNS lookup of the source domain. The finding was rated blocking, and the design below is the answer to it.

What DNS is allowed to decide

  • Known domains cost nothing. Gmail, iCloud and similar addresses answer from a table, with no query, so no DNS answer can change them.
  • An MX record picks, it does not write. The hosts of the lowest preference are matched by whole labels against a fixed table of zones. A match names a provider whose servers come from Senderban's own table, so a forged record reaches a known provider at worst. MXroute is the one exception: its mailbox server is the MX host, so that name is kept, but only one label inside MXroute's own zone.
  • An unknown mail host is asked. At most three ManageSieve probes run side by side, 5 seconds each, in the order of RFC 5804 §1.8, with the primary MX added in between because most servers run both. A probe sends nothing of the person's and reads the answer behind verified TLS. Then the _imaps._tcp target of RFC 6186, on port 993. Then "unknown".
  • Inside the mail domain is evidence, outside is none. This follows RFC 6186 §6. Someone who can forge a DNS answer still needs a public certificate for the name, and for a name inside the person's domain that takes control of the domain. So a name from DNS fills the form only when it is the domain itself or below it, and never on a public suffix, where strangers register the names below. One limit is written down: a subdomain the domain has handed to someone else, or left dangling, counts as inside. A name outside comes back as data: the page says records can be forged, sends the person to their provider's welcome mail, and leaves the field empty.
  • The process that asks for the password checks for itself. The main process compares the server with the address's domain; for an outside name the dialog in front of the password opens with "This server is not part of example.com." A preset and a server Senderban's table names for that domain get no note, because a note that is false on a big provider teaches people to click past it.

What leaves the device

  • The DNS query carries the domain. The rest of the address and the password do not leave, and nothing is stored or logged: the log line has the result kind, the time and counts, never the domain or a server. The privacy policy says so.
  • A probed server sees the person's IP address and nothing else of theirs.
  • Only the system's resolver is used: no DNS over HTTPS service of ours and no list of ours, so no new party learns the domain. One caveat is written down too: Node's resolver reads the system's server list but not the hosts file, and whether a system set to encrypted DNS applies here is not known.

Not being steered after the check

A name that passes the check could still resolve to something else when the connection opens: DNS rebinding. So the probe's socket takes its address from one lookup, publicAddressLookup, which drops private, loopback and link-local answers, checks an IPv4 address written as IPv6 against the same rules, and drops the translation prefixes that carry an IPv4 address (such as 64:ff9b::/96). A name cannot answer one thing to the check and another to the connection. A name from DNS must also pass the same public host name check as a typed one, SRV ports are limited to 4190, 2000 and 993, and a greeting stops at 8 KiB.

The button runs on a click only, one at a time and at most six a minute, and ends with the window or after 10 seconds. A mail never starts it. Source: detect.ts, live.ts.

Where it departs from the standards

RFC 6186 §6 asks two things: check that a target lies in the queried domain, which is done, and verify a target outside it with the user before any connection. The second is a departure: a ManageSieve probe connects first. It follows the person's click, carries nothing of theirs and gives away only their IP address, and a name outside the domain never reaches the form. The _imaps._tcp target is never connected to. Three smaller departures, all in ADR 0018: the primary MX is probed between the SRV target and the domain, only the first SRV target is taken where RFC 5804 §1.8 tries each one, and the SRV-ID comparison of RFC 7817 §3 is not done, which only makes fewer certificates pass.

Measured

On 1 November 2026, in Electron 45.1, on public DNS, without signing in anywhere:

Case Result Time
Known domain from the table 12 ms
MX in the table provider 31-219 ms
Public ManageSieve, not in the table the domain itself 534-684 ms
Nothing found, port 4190 filtered unknown about 5.2 s

Five real ManageSieve servers answered a probe in 294 to 1,229 ms, so the 5-second limit leaves a margin of four. One click costs at most 3 DNS queries and 3 TLS connections, and nothing runs between clicks, so the cost does not grow with the number of accounts.

What it costs

  • A domain hosted under another company's name pays one paste: its server is outside the domain, so the person copies it from their welcome mail.
  • A domain behind a mail gateway shows the gateway in its MX record and reads as unknown. The person picks the provider by hand, as before the button existed.
  • A name lookup cannot be cancelled: a stuck system resolver can hold up to 3 of the 4 threads of Node's pool past the deadline. The click is freed either way.
  • Not measured: a forged answer on a real network with a real certificate, and adding an account from a suggestion at any provider.

The general lesson: when an answer can be forged, decide what it is allowed to change before deciding how to verify it. Here DNS may pick from a list or point inside the person's own domain, and nothing else.
